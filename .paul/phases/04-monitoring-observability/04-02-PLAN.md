<objective>
## Goal
Enhance the health check endpoint with comprehensive subsystem checks (database, pg-boss, memory), configure Docker-level health monitoring with proper thresholds, and provide a checkpoint for external uptime monitoring setup.

## Purpose

AEGIS is moving toward real UCB pilot deployments. The current health endpoint only checks database connectivity — it can't detect a failed job queue, memory exhaustion, or degraded external services. Enhanced health checks give operators and Docker orchestration a richer signal for automated restart and alerting decisions. External uptime monitoring ensures issues are detected even if the server itself is unresponsive.

## Output

- Enhanced /api/health endpoint checking database, pg-boss queue health, and process memory
- Structured JSON response with per-subsystem status and response time
- Docker healthcheck using the enhanced endpoint (already configured, verified working)
- External uptime monitoring configured (human action — requires external service setup)
  </objective>

<acceptance_criteria>

## AC-1: Enhanced Health Endpoint Returns Subsystem Status

```gherkin
Given the AEGIS app is running
When GET /api/health is called
Then the response includes status for each subsystem: database, jobQueue, memory
And each subsystem reports "ok" or "error" with response time in milliseconds
And the overall status is "ok" only when all critical subsystems pass
And the response includes the x-request-id header from middleware
```

## AC-2: Health Endpoint Degrades Gracefully

```gherkin
Given the database is unreachable
When GET /api/health is called
Then the response returns 503 with database status "error"
And the job queue check is skipped (depends on database)
And the memory check still reports independently
And the response completes within 5 seconds (no hanging)
```

## AC-3: Memory Usage Reported

```gherkin
Given the AEGIS app is running
When GET /api/health is called
Then the response includes memory.heapUsedMB and memory.heapTotalMB
And memory.status is "ok" when heap usage is below 90% of total
And memory.status is "warning" when heap usage exceeds 90%
```

## AC-4: Docker Healthcheck Uses Enhanced Endpoint

```gherkin
Given AEGIS is deployed via Docker
When the container healthcheck runs
Then it calls /api/health and interprets the HTTP status code
And containers restart automatically on repeated 503 responses
```

<task type="auto">
  <name>Task 1: Enhance health endpoint with subsystem checks</name>
  <files>src/app/api/health/route.ts</files>
  <action>
    Rewrite the health endpoint to check multiple subsystems:

    1. Keep the existing pg Pool singleton pattern (max 1 connection, 3s timeout)

    2. Add database check (existing):
       - Execute `SELECT 1` via the pool
       - Measure response time in ms
       - Return { status: "ok"|"error", responseTimeMs: number }

    3. Add pg-boss queue check:
       - Only run if database check passed (pg-boss uses the same database)
       - Query: `SELECT count(*) as active FROM pgboss.job WHERE state = 'active' OR state = 'created'`
       - This is a lightweight check that pg-boss tables exist and are accessible
       - Wrap in try/catch — if pgboss schema doesn't exist, report "unavailable" not "error"
       - Return { status: "ok"|"unavailable"|"error", activeJobs: number }

    4. Add memory check:
       - Use process.memoryUsage() (available in nodejs runtime)
       - Calculate heap usage percentage: heapUsed / heapTotal * 100
       - Status "ok" if < 90%, "warning" if >= 90%
       - Return { status: "ok"|"warning", heapUsedMB: number, heapTotalMB: number, usagePercent: number }

    5. Determine overall status:
       - "ok" if database is connected and no critical failures
       - "degraded" if non-critical subsystems have issues (memory warning, pg-boss unavailable)
       - "error" if database check fails
       - HTTP 200 for "ok" or "degraded", 503 for "error"

    6. Include request ID from headers:
       - Read x-request-id from request headers (set by middleware in Plan 04-01)
       - Include in response body

    7. Response shape:
       ```json
       {
         "status": "ok" | "degraded" | "error",
         "timestamp": "ISO-8601",
         "requestId": "uuid",
         "checks": {
           "database": { "status": "ok", "responseTimeMs": 2 },
           "jobQueue": { "status": "ok", "activeJobs": 0 },
           "memory": { "status": "ok", "heapUsedMB": 120, "heapTotalMB": 512, "usagePercent": 23.4 }
         },
         "version": "4.0.0"
       }
       ```

    8. Log health check results using the existing logger:
       - logger.info for successful checks
       - logger.warn for degraded checks
       - logger.error for failed checks

    Avoid:
    - Do NOT import pg-boss directly — just query the pgboss schema tables via the existing pool
    - Do NOT make the endpoint slow — total timeout should be 5 seconds max
    - Do NOT check S3/SES connectivity (they're optional services, not critical health indicators)
    - Do NOT expose sensitive data (connection strings, passwords) in the response
    - Do NOT change the route path (/api/health must remain the same)
    - Do NOT add authentication to the health endpoint (load balancers need unauthenticated access)

  </action>
  <verify>
    - pnpm build succeeds
    - curl http://localhost:3000/api/health returns JSON with checks.database, checks.jobQueue, checks.memory
    - Response includes x-request-id header
    - Response includes version field
    - HTTP 200 when all checks pass
  </verify>
  <done>AC-1 satisfied (subsystem checks), AC-2 satisfied (graceful degradation), AC-3 satisfied (memory reporting)</done>
</task>

<task type="checkpoint:human-action" gate="blocking">
  <what>Set up external uptime monitoring</what>
  <context>
    External uptime monitoring provides alerting when the entire server is down (Docker can't self-heal if the host is unreachable). This requires signing up for a monitoring service and configuring it to check the health endpoint.

    Recommended free options:
    1. **UptimeRobot** (free tier: 50 monitors, 5-min intervals) — uptimerobot.com
    2. **Better Uptime** (free tier: 10 monitors, 3-min intervals) — betteruptime.com
    3. **Freshping** (free tier: 50 monitors, 1-min intervals) — freshping.io

    Configuration:
    - Monitor URL: https://aegis.nexlyadvisory.com/api/health
    - Check type: HTTP(S) keyword (check for `"status":"ok"` or just HTTP 200)
    - Check interval: 5 minutes
    - Alert contacts: Your email address
    - Alert on: Down (HTTP 5xx or timeout)

    This is a human action because it requires creating an account on an external service and configuring alert contacts.

  </context>
  <resume-signal>Type "done" when uptime monitoring is configured, or "skip" to defer to later</resume-signal>
