# RBAC role → permission matrix

Generated by hand from `src/lib/permissions.ts` (not by `docs:reference` —
this file lives outside the generator's four managed files and is not
byte-checked by `docs:check`; re-derive it by hand if `permissions.ts`
changes). 17 roles, 78 permissions, verified by counting the source file at
generation time.

Roles are multi-assignable — a user's effective permission set is the
**union** across every role they hold (`getPermissions()`), not the
permissions of a single "primary" role. `hasPermission()` checks with
`roles.some(...)`, never `roles[0]` or `role ===`. See
[Invariant 3 in `docs/architecture.md`](../architecture.md#invariant-3--authorization)
for how this union is enforced in practice.

## Reserved, unassigned patterns worth knowing

- **Maker-checker is not a permission** — `canApproveObservation(userId, observation)`
  in `permissions.ts` checks `userId !== observation.createdById` at the
  transaction level. A user with `observation:approve` still cannot approve
  their own observation; the permission grants the *capability*, the
  maker-checker function is a separate runtime gate. See
  [`docs/explanation/state-machines-and-maker-checker.md`](../explanation/state-machines-and-maker-checker.md).
- **A permission string with no role attached is dead code**, not a future
  hook — if you add a `Permission` union member, add it to at least one
  role's array in the same change, or it can never be granted.
