# AEGIS v3.0 Roadmap

**Vision:** Transform AEGIS from an observation tracking system into an intelligent compliance platform with predictive analytics, automated workflows, and ecosystem integration.

**Target Completion:** Q4 2026
**Prerequisites:** v2.1 shipped with all core features, pilot deployments underway

---

## Executive Summary

v3.0 builds on the solid foundation of v2.1 (working core MVP with auth, multi-tenancy, observation lifecycle, dashboards, and reports) to add:

1. **Intelligence Layer** — AI/ML-powered compliance gap detection, anomaly detection, and risk scoring
2. **Advanced Analytics** — Custom report builder, trend analysis, peer benchmarking, DAKSH predictor
3. **Automation Engine** — Workflow automation, escalation rules, SLA tracking, recurring templates
4. **Integration Hub** — CBS data import, RBI XBRL filing, CRILC reporting
5. **Mobile First** — PWA for field auditors with offline evidence capture
6. **Multi-Bank Ecosystem** — Federation views, inter-bank audit sharing, regulatory body portal
7. **Enterprise Security** — SOC2 readiness, encryption at rest, field-level encryption, enhanced audit logging

**Why Now:**

- v2.1 pilot deployments will validate core workflows and reveal the next tier of requirements
- UCB market is moving from "do we need audit software?" to "what advanced features justify premium pricing?"
- RBI is tightening supervisory expectations (DAKSH, RBIA, cyber security) — AI-powered gap detection becomes a competitive moat
- Larger UCBs (Tier I/II) have CBS systems and need integration; smaller UCBs (Tier III/IV) need mobile field audit

## 1. AI/ML Features

### Business Justification

**Problem:**

- UCB audit teams spend 40% of fieldwork time manually checking for compliance gaps across 200+ RBI Master Directions
- Anomaly detection (e.g., "Branch X has 3x the average KYC violations") is currently manual pattern recognition
- New RBI circulars require CAEs to manually assess impact across existing audit universe
- Risk scoring is subjective and inconsistent across auditors

**Value:**

- **AI-powered compliance gap detection:** Auto-identifies missing controls by comparing bank's documented processes against RBI requirements → 60% reduction in checklist review time
- **Anomaly detection in audit findings:** Flags unusual patterns (repeat findings at specific branches, severity clusters) → early warning for systemic issues
- **Automated RBI circular impact analysis:** NLP on new circulars maps to existing compliance requirements → CAE gets "Impact: 12 existing audits need scope expansion" within 24 hours of circular release
- **Smart risk scoring:** ML model trained on historical observation data predicts risk ratings with 85%+ consistency → reduces auditor subjectivity, improves DAKSH score accuracy

**ROI for UCBs:**

- Tier I/II UCBs: Justify premium pricing (Rs 8-12 Lakh/year vs. Rs 4 Lakh base)
- Tier III/IV UCBs: Differentiation vs. spreadsheets ("AI-powered audit" is a board-level selling point)
- All tiers: Improved DAKSH scores → reduced RBI supervisory intervention risk

### 1.1 AI-Powered Compliance Gap Detection

**Technical Approach:**

**Phase 1: Rule-Based Foundation (P0)**

1. Build compliance requirement graph:
   - Nodes: RBI Master Directions (KYC, CRAR, ALM, etc.)
   - Edges: Dependencies (e.g., ALM policy requires board approval → Board governance requirement)
   - Store as adjacency list in PostgreSQL `ComplianceRequirementDependency` table
2. Implement coverage analyzer:
   - Input: Bank's current observations, audit plans, compliance certifications
   - Algorithm: Graph traversal to identify uncovered nodes
   - Output: "Gap Report" — requirements with no associated observations in last 12 months
3. Severity scoring:
   - Priority 1: RBI mandated items with explicit deadlines
   - Priority 2: Tier-specific requirements
   - Priority 3: Best practice recommendations
4. UI: New dashboard widget "Compliance Coverage Map" (heatmap visualization)

**Phase 2: ML-Powered Pattern Recognition (P1)**

1. Training data:
   - Historical observations from 20+ pilot UCBs (anonymized)
   - RBI circulars mapped to requirement categories
   - DAKSH assessment data (public UCB scorecards from RBI website)
2. Model: Random Forest classifier
   - Features: Bank tier, asset size, geographic region, historical violation categories
   - Target: High-risk requirement categories for this bank profile
3. Weekly batch job:
   - Run ML model to predict high-risk areas
   - Generate prioritized audit plan suggestions
   - CAE reviews and approves/modifies
4. Feedback loop:
   - Track which suggestions led to actual findings
   - Retrain model quarterly with new data

**Phase 3: NLP for Requirement Extraction (P2)**

1. Use OpenAI GPT-4 API (or similar) to:
   - Parse new RBI circulars (PDF → structured JSON)
   - Extract compliance obligations ("shall", "must", "required to")
   - Map to existing requirement taxonomy
2. Auto-create draft compliance requirements:
   - CAE reviews before adding to registry
   - Links back to source circular (page number, clause)
3. Impact analysis:
   - Compare new requirements against current audit universe
   - Identify affected audit engagements
   - Suggest scope modifications

**Estimated Effort:**

- Phase 1 (Rule-based): 3 months, 1 developer + 1 domain expert
  - Week 1-2: Requirement dependency modeling
  - Week 3-6: Coverage analyzer + graph traversal
  - Week 7-10: Dashboard widget + gap report UI
  - Week 11-12: Testing with pilot data
- Phase 2 (ML): 4 months, 1 ML engineer + 1 developer
  - Month 1: Data pipeline (anonymize, normalize, label)
  - Month 2: Feature engineering + model training
  - Month 3: Batch job integration + prediction API
  - Month 4: UI for predictions + feedback loop
- Phase 3 (NLP): 3 months, 1 developer (using GPT-4 API)
  - Month 1: PDF parsing pipeline + circular database
  - Month 2: Requirement extraction + mapping
  - Month 3: Impact analysis + CAE review workflow

**Total: 10 months (can parallelize Phase 1 and Phase 2 planning)**

**Priority:** P0 (Phase 1), P1 (Phase 2), P2 (Phase 3)

**Dependencies:**

- Phase 1: v2.1 compliance registry
- Phase 2: Anonymized pilot data from 20+ banks (requires pilot program success)
- Phase 3: RBI circular database (scrape from rbi.org.in or manual upload)

**Success Metrics:**

- Phase 1: 100% coverage detection accuracy vs. manual CAE review (validate with 5 pilot UCBs)
- Phase 2: 70%+ precision on high-risk area predictions (measured by findings/audit hour)
- Phase 3: 90%+ requirement extraction accuracy (manual validation sample of 50 circulars)

### 1.2 Anomaly Detection in Audit Findings

**Technical Approach:**

**Statistical Baseline (P1)**

1. Time-series analysis on observation data:
   - Calculate per-branch, per-category baselines (30/60/90-day moving averages)
   - Metrics: observation count, severity distribution, closure time, repeat rate
2. Outlier detection algorithms:
   - Z-score method: Flag observations >2 standard deviations from branch baseline
   - IQR method: Flag observations outside 1.5x interquartile range
   - Isolation Forest: Unsupervised ML to detect multi-dimensional anomalies
3. Alert generation:
   - CAE dashboard widget: "Anomalies This Week" table
   - Email digest: Weekly summary of flagged patterns
4. Drill-down capability:
   - Click anomaly → view observation timeline + comparative chart
   - "Why flagged?" explanation: "Branch X: 12 KYC observations vs. bank average 3.2"

**ML-Based Anomaly Detection (P2)**

1. Autoencoder neural network:
   - Train on "normal" observation patterns from 100+ audits
   - Input: Observation features (severity, category, branch, auditor, response time)
   - Reconstruction error threshold → anomaly score
2. Contextual anomalies:
   - Same absolute value may be normal for one branch, anomalous for another
   - Model learns bank-specific and branch-specific patterns
3. Real-time scoring:
   - Score every new observation on submission
   - High anomaly score → notification to Audit Manager for expedited review
4. Feedback mechanism:
   - Manager marks false positives → retrain model

**Estimated Effort:**

- Statistical Baseline: 2 months, 1 developer
  - Week 1-3: Time-series pipeline + baseline calculation
  - Week 4-5: Outlier detection algorithms
  - Week 6-7: Dashboard widget + alerts
  - Week 8: Testing + tuning thresholds
- ML-Based: 3 months, 1 ML engineer
  - Month 1: Data preprocessing + feature engineering
  - Month 2: Autoencoder training + hyperparameter tuning
  - Month 3: Real-time scoring API + feedback loop

**Total: 5 months (sequential)**

**Priority:** P1

**Dependencies:**

- Historical observation data from 20+ pilot UCBs (6+ months of usage)
- v2.1 observation lifecycle + dashboards

**Success Metrics:**

- 80%+ true positive rate on known anomalies (validate with retrospective audit data)
- <10% false positive rate (manager time wasted on spurious alerts)
- 50% reduction in undetected systemic issues (measured by RBI inspection surprise findings)

### 1.3 Automated RBI Circular Impact Analysis

**Technical Approach:**

**Document Processing Pipeline (P1)**

1. RBI circular ingestion:
   - Web scraper: Monitor rbi.org.in/Scripts/BS_CircularIndexDisplay.aspx
   - PDF parser: Extract text using pdfplumber or Apache Tika
   - Store in `RBICircular` table: date, reference number, subject, full text, PDF URL
2. NLP processing:
   - Use spaCy or GPT-4 API for:
     - Named entity recognition: Extract compliance keywords (KYC, CRAR, NPA, etc.)
     - Dependency parsing: Identify obligation phrases ("shall maintain", "required to report")
     - Classification: Categorize circular (prudential norms, operational guidelines, reporting)
3. Requirement mapping:
   - Match extracted keywords to existing `ComplianceRequirement` taxonomy
   - Fuzzy matching + embedding similarity (sentence-transformers)
   - Output: List of potentially impacted requirements

**Impact Assessment Engine (P1)**

1. Audit universe analysis:
   - For each impacted requirement, find associated:
     - Audit engagements (planned or in-progress)
     - Historical observations
     - Compliance certifications
2. Scope gap detection:
   - New circular obligation not covered by any current audit scope → "Scope gap"
   - Existing audit scope needs expansion → "Update required"
3. Auto-generate draft impact report:
   - Affected engagements: List with proposed scope modifications
   - New compliance tasks: Draft requirements for CAE approval
   - Timeline implications: Deadlines from circular vs. current audit plan
4. CAE review workflow:
   - Email notification: "New RBI circular RBI/2026/123 may affect 4 audits"
   - In-app: Review impact report, approve/modify suggested actions
   - One-click: Add new requirements to compliance registry + update audit scopes

**Estimated Effort:**

- 4 months, 1 developer + 1 domain expert
  - Month 1: Web scraper + PDF parser + database schema
  - Month 2: NLP pipeline (spaCy + GPT-4 integration)
  - Month 3: Requirement mapping + impact engine
  - Month 4: CAE review UI + one-click action workflow

**Total: 4 months**

**Priority:** P1

**Dependencies:**

- v2.1 compliance registry + audit planning
- RBI circular archive (historical circulars for validation)
- OpenAI API access (or equivalent NLP service)

**Success Metrics:**

- 90%+ circular categorization accuracy (manual validation sample)
- 80%+ requirement mapping precision (CAE confirms suggestions)
- 100% of circulars processed within 48 hours of RBI publication
- 70% reduction in CAE time spent on circular review (manual tracking before/after)

### 1.4 Smart Risk Scoring

**Technical Approach:**

**Feature Engineering (P1)**

1. Extract features from historical observations:
   - Observation characteristics: Severity, category, branch tier, department
   - Audit context: Audit type, auditor experience level, time in cycle
   - Auditee response: Response time, evidence quality, revision count
   - Historical patterns: Repeat finding, branch history, category frequency
2. Target variable:
   - Final severity rating (as confirmed by CAE on closure)
   - Alternative: DAKSH impact flag (did this observation affect DAKSH score?)
3. Feature normalization:
   - Encode categorical variables (one-hot or target encoding)
   - Scale numerical variables (StandardScaler)

**Model Training (P1)**

1. Algorithm selection:
   - Start with Gradient Boosting (XGBoost or LightGBM)
   - Good for tabular data, handles missing values, provides feature importance
2. Train/validation split:
   - 80/20 split on historical observations (minimum 10,000 observations)
   - Stratified by severity to handle class imbalance
3. Hyperparameter tuning:
   - Bayesian optimization using Optuna
   - Cross-validation to prevent overfitting
4. Model evaluation:
   - Accuracy, precision, recall per severity class
   - Confusion matrix analysis
   - Feature importance ranking (explainability)

**Production Integration (P1)**

1. Prediction API:
   - When auditor creates observation (Draft state), API returns suggested severity
   - UI shows: "Recommended: High (85% confidence) based on similar KYC findings at Tier III branches"
   - Auditor can accept or override with justification
2. Batch re-scoring:
   - Weekly job: Re-score all open observations with updated model
   - Alert if severity mismatch (model suggests Critical but observation is Medium)
3. Model retraining:
   - Monthly: Retrain model with new observations from last 30 days
   - Version control: Track model performance over time
   - Rollback if new model underperforms

**Explainability (P2)**

1. SHAP (SHapley Additive exPlanations):
   - Show why model recommended specific severity
   - UI: "Severity influenced by: Repeat finding (+0.3), Branch NPA ratio (+0.2), Response delay (+0.15)"
2. Counterfactual explanations:
   - "If auditee had responded 5 days earlier, severity would be Medium instead of High"

**Estimated Effort:**

- 3 months, 1 ML engineer + 1 developer
  - Month 1: Feature engineering + data pipeline
  - Month 2: Model training + evaluation + hyperparameter tuning
  - Month 3: Prediction API + UI integration + batch re-scoring

**Total: 3 months**

**Priority:** P1

**Dependencies:**

- Minimum 10,000 historical observations (6+ months of pilot data from 20+ UCBs)
- v2.1 observation lifecycle
- Python ML stack deployment (FastAPI microservice or AWS Lambda)

**Success Metrics:**

- 85%+ accuracy on severity prediction (validation set)
- 70%+ auditor acceptance rate (measure via "override with justification" frequency)
- 30% reduction in CAE severity revisions (fewer observations sent back for re-assessment)

   - Study RBI's UCB supervisory manual (published on rbi.org.in)

2. Map AEGIS data to DAKSH parameters:
   - **Capital adequacy:** Compliance with CRAR requirement (from compliance registry)
   - **Asset quality:** NPA-related observations count + severity
   - **Management:** Governance-related observations, board meeting frequency
   - **Earnings:** Revenue audit findings
   - **Liquidity:** ALM compliance status
   - **Systems & controls:** IT audit findings, internal control observations
3. Weighted scoring:
   - Assign weights to each category (based on RBI manual)
   - Calculate composite score (0-100 scale, aligned with DAKSH bands: A/B/C/D)

**Prediction Algorithm (P1)**

1. Real-time score calculation:
   - As observations are created/closed, update DAKSH parameter values
   - Recalculate composite score
2. Historical trend:
   - Show DAKSH score trend over last 12 months
   - Identify declining categories
3. Scenario analysis:
   - "If you close 5 High-severity IT observations, score improves from 68 to 72"

**Gap Analysis (P1)**

1. Compare predicted score to RBI's published DAKSH bands:
   - Band A (80-100): Minimal supervisory intervention
   - Band B (60-79): Enhanced supervision
   - Band C (40-59): Corrective action

2. Actionable recommendations:
   - "To move from Band B to Band A, you need to: Close 8 High-severity observations, achieve 90%+ ALM compliance"
3. Priority matrix:
   - Rank observations by DAKSH impact ("Closing this Critical CRAR observation adds 4 points")

**Technical Implementation:**

1. Backend:
   - DAKSH calculation engine (pure function: observations + compliance data → score)
   - Store in `DAKSHScore` table: score, category_scores, calculated_at, tenant_id
   - Recalculate on every observation state change (async job)
2. Frontend:
   - DAKSH predictor page: `/reports/daksh`
   - Radial gauge chart for composite score
   - Category breakdown (6 sub-scores)
   - Gap analysis table + recommendations

**Estimated Effort:**

- 2 months, 1 developer + 1 domain expert (to validate DAKSH mapping)
  - Month 1: DAKSH model reverse-engineering + scoring algorithm

**Total: 2 months**

### 3.1 Automated Observation Routing

**Technical Approach:**

**Routing Rules Engine (P1)**

1. Rule definition UI:
   - Admin configures routing rules via Settings > Workflow Automation
   - Rule format: IF [condition] THEN [assign to role/user]
   - Conditions:
     - Observation category (KYC → Compliance Officer)
     - Branch/Department (Branch A observations → Branch A Manager)
     - Severity (Critical → CAE)
     - Audit type (IT Audit → CTO)
     - Keyword in observation text (contains "loan" → Credit Manager)
2. Rule priority:
   - Rules evaluated in order (drag-to-reorder UI)
   - First matching rule wins
   - Fallback: Unmatched observations assigned to default role (Audit Manager)
3. Rule validation:
   - Prevent circular assignments
   - Warn if rule assigns to non-existent user

**Auto-Assignment on State Transition (P1)**

1. Trigger: When observation moves to "Issued" state
2. Evaluate routing rules:
   - Match observation attributes against rule conditions

## 4. Integration Layer

**Value:**

- **RBI XBRL filing integration:** Export audit-verified financial data in XBRL format → compliance with RBI reporting requirements
- **CRILC reporting hooks:** Audit trail for large credit exposures → seamless CRILC submission

**ROI for UCBs:**

- Tier I/II: Critical differentiator (these UCBs have CBS systems)
- Tier III/IV: Optional (many still on manual/semi-automated systems)
- All tiers: Reduced RBI filing errors → lower regulatory risk

**Data Security (P0)**

### 7.2 Encryption at Rest

**Technical Approach:**

**PostgreSQL Transparent Data Encryption (TDE) (P1)**

1. AWS RDS encryption:
   - Enable RDS encryption (AES-256) for PostgreSQL instance
   - Encrypts data files, backups, snapshots
   - Transparent to application (no code changes)
2. Key management:
   - AWS KMS (Key Management Service) for encryption keys
   - Automatic key rotation (annual)
3. Backup encryption:
   - All PostgreSQL backups encrypted at rest in S3

**Application-Level Encryption (P2)**

- For additional layer (if TDE insufficient), use pgcrypto extension
- Encrypt specific columns (PAN, Aadhaar) at application level
- Requires code changes (encrypt on write, decrypt on read)

**S3 Encryption (P0)**

- Already implemented: SSE-S3 (Server-Side Encryption with S3-managed keys)
- Upgrade: SSE-KMS (S3 encryption with AWS KMS keys) for key rotation

**Technical Implementation:**

1. AWS RDS:
   - Enable encryption via AWS Console or Terraform
   - Requires database migration (cannot enable encryption on existing unencrypted RDS instance)
   - Migration: Snapshot → Restore to encrypted instance → Update DNS
2. Code changes:
   - None for TDE (transparent)
   - For application-level encryption: Add encrypt/decrypt helpers
3. Testing:
   - Verify encryption via AWS Console (RDS encryption status)
   - Verify backups encrypted

**Estimated Effort:**

- 2 weeks, 1 DevOps engineer
  - Week 1: RDS encryption enable + migration planning
  - Week 2: Migration execution + testing + DNS cutover

**Total: 2 weeks**

**Priority:** P0 (baseline security, quick win)

**Dependencies:**

- AWS KMS setup
- Downtime window for migration (4-6 hours)

**Success Metrics:**

- 100% data encrypted at rest (verified via AWS Console)
- 0 performance degradation (encryption overhead <5%)
- SOC 2 control satisfied

### 7.3 Field-Level Encryption for Sensitive Data

**Technical Approach:**

**Sensitive Fields (P1)**

1. Identify PII/sensitive fields:
   - PAN (Permanent Account Number)
   - Aadhaar number
   - Loan account numbers (if CBS integration enabled)
   - Depositor names (if CBS integration enabled)
   - Bank account numbers in evidence files
2. Encryption scope:
   - Encrypt only fields above (not entire observation text)
   - Balance: Security vs. searchability (encrypted fields not searchable)

**Encryption Library (P1)**

1. Use: Node.js crypto module (AES-256-GCM)
2. Key management:
   - Master key stored in AWS Secrets Manager
   - Data Encryption Key (DEK) per tenant (envelope encryption)
   - Master key encrypts DEKs, DEKs encrypt data
3. Rotation:
   - Annual master key rotation
   - Re-encrypt all data with new DEK (background job)

**Implementation (P1)**

1. Database schema:
   - New columns: `pan_encrypted`, `aadhaar_encrypted` (store ciphertext + IV)
   - Migrate existing plaintext data to encrypted columns
2. Code changes:
   - Encrypt on write: `encrypt(plaintext, dek) → ciphertext`
   - Decrypt on read: `decrypt(ciphertext, dek) → plaintext`
   - Search limitation: Cannot search encrypted fields (trade-off)
3. Audit logging:
   - Log every decryption attempt (who, when, which field)

**Technical Implementation:**

1. Backend:
   - Encryption helpers: `src/lib/encryption.ts`
   - Key retrieval: AWS Secrets Manager client
   - Server actions: Encrypt before Prisma insert, decrypt after SELECT
2. Database:
   - Add encrypted columns (migration)
   - Drop plaintext columns after migration complete

**Estimated Effort:**

- 1 month, 1 developer
  - Week 1: Encryption library + key management
  - Week 2: Schema migration + encrypt existing data
  - Week 3: Code changes (encrypt/decrypt on read/write)
  - Week 4: Testing + decryption audit logging

**Total: 1 month**

**Priority:** P1

**Dependencies:**

- AWS Secrets Manager setup
- Encryption at rest (7.2) as baseline

**Success Metrics:**

- 100% sensitive fields encrypted (verified via manual inspection)
- 0 plaintext PII in database dumps
- <10ms decryption latency (performance test)

### 7.4 Comprehensive Audit Logging Enhancements

**Technical Approach:**

**Field-Level Change Tracking (P1)**

1. Current state (v2.1):
   - Audit log records: entity_type, entity_id, action, user, timestamp
   - Does NOT record: Which fields changed, old value, new value
2. Enhanced logging:
   - Before update: `{ severity: "High", status: "Issued" }`
   - After update: `{ severity: "Critical", status: "Issued" }`
   - Log: `{ field: "severity", old_value: "High", new_value: "Critical" }`
3. Diff calculation:
   - Compare before/after snapshots
   - Store only changed fields (not entire object)

**Audit Log Schema (P1)**

1. New columns:
   - `field_changes`: JSONB array of { field, old_value, new_value }
   - `snapshot_before`: JSONB (full entity state before change)
   - `snapshot_after`: JSONB (full entity state after change)
2. Example:
   ```json
   {
     "entity_type": "Observation",
     "entity_id": "obs-123",
     "action": "UPDATE",
     "field_changes": [
       { "field": "severity", "old_value": "High", "new_value": "Critical" },
       { "field": "status", "old_value": "Issued", "new_value": "Response" }
     ],
     "user_id": "user-456",
     "timestamp": "2026-03-15T10:30:00Z"
   }
   ```

**Immutable Audit Log (P0)**

1. Already implemented: Append-only table, no UPDATE/DELETE
2. Enhancement: Cryptographic hash chain
   - Each log entry includes hash of previous entry
   - Tamper detection: If hash chain breaks, log was modified
   - Algorithm: SHA-256 hash of (previous_hash + current_entry)

**Audit Log Viewer Enhancements (P1)**

1. Field-level history:
   - Observation detail page: "Severity changed from High to Critical by user-456 on 2026-03-15"
   - Timeline shows field changes, not just state transitions
2. Advanced search:
   - Search by field name: "Show all changes to severity field"
   - Search by old/new value: "Show all observations changed to Critical"
3. Export:
   - Excel export of audit log with field changes

**Performance Optimization (P1)**

1. Partitioning:
   - Partition audit log table by month (PostgreSQL partitioning)
   - Improve query performance on large logs (millions of rows)
2. Archival:
   - After 2 years, archive old logs to S3 (compliance: 10-year retention)
   - Keep in PostgreSQL for 2 years (active queries)

**Technical Implementation:**

1. Database:
   - Add columns: field_changes (JSONB), snapshot_before (JSONB), snapshot_after (JSONB), hash (VARCHAR)
   - Partition by month: `AuditLog_2026_03`, `AuditLog_2026_04`, etc.
2. Backend:
   - Diff calculation: `calculateDiff(before, after) → field_changes`
   - Hash calculation: `calculateHash(previous_hash, current_entry) → hash`
   - Server action: `logChange(entityType, entityId, before, after, action, userId)`
3. Frontend:
   - Enhanced audit log viewer: `/audit-trail` (with field change display)

**Estimated Effort:**

- 1.5 months, 1 developer
  - Week 1-2: Schema changes + diff calculation
  - Week 3-4: Hash chain implementation + tamper detection
  - Week 5-6: Enhanced viewer UI + partitioning

**Total: 1.5 months**

**Priority:** P1

**Dependencies:**

- v2.1 audit logging infrastructure

**Success Metrics:**

- 100% field-level change coverage (all entity updates logged)
- Hash chain integrity verified (no breaks detected)
- 90% CAE satisfaction with audit trail (survey: "Can you find what changed?")
