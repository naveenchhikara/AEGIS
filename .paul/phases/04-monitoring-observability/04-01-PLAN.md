<objective>
## Goal
Integrate Sentry error tracking and request ID propagation into the AEGIS platform, providing production visibility into unhandled errors, server-side exceptions, and request tracing.

## Purpose

AEGIS is preparing for real UCB pilot deployments. Without error tracking, production issues are invisible — errors go to browser console (client) or stdout (server) with no aggregation, alerting, or correlation. Sentry provides the industry-standard solution for capturing, deduplicating, and alerting on errors. Request IDs enable tracing a user's action across logs.

## Output

- Sentry SDK configured for Next.js 16 (client, server, edge)
- Unhandled errors automatically captured and reported
- Request ID generated per request and propagated through logs
- Error boundaries wire to Sentry with user/tenant context
- Graceful degradation when Sentry DSN not configured (like S3/SES pattern)
  </objective>

## AC-1: Sentry Captures Client-Side Errors

```gherkin
Given the AEGIS app is running with SENTRY_DSN configured
When an unhandled JavaScript error occurs in a client component
Then the error is captured by Sentry with error message, stack trace, and digest
And the error appears in the Sentry dashboard within 30 seconds
```

## AC-2: Sentry Captures Server-Side Errors

```gherkin
Given the AEGIS app is running with SENTRY_DSN configured
When a server action or API route throws an unhandled exception
Then the error is captured by Sentry with stack trace and request context
And the error includes tenantId and userId tags when available from session
```

## AC-3: Graceful Degradation Without Sentry

```gherkin
Given SENTRY_DSN is not set in environment variables
When the application starts and processes requests
Then no Sentry-related errors appear in logs
And error boundaries continue to function normally (console.error fallback)
And the build succeeds without Sentry configuration
```

## AC-4: Request ID Propagation

```gherkin
Given a request arrives at the AEGIS application
When the middleware processes the request
Then a unique x-request-id header is added to the response
And the request ID is available downstream for logging via headers()
```

  <action>
    1. Install @sentry/nextjs:
       - `pnpm add @sentry/nextjs`

    2. Add Sentry env vars to src/env.ts:
       - Server: SENTRY_DSN as z.string().url().optional() (optional like S3/SES)
       - Server: SENTRY_AUTH_TOKEN as z.string().optional() (for source maps, CI only)
       - Client: NEXT_PUBLIC_SENTRY_DSN as z.string().url().optional()
       - Add to runtimeEnv mapping
       - Sentry DSN follows same optional pattern as AWS vars

    3. Create sentry.client.config.ts (project root):
       - Import * as Sentry from "@sentry/nextjs"
       - Guard: only init if NEXT_PUBLIC_SENTRY_DSN is set
       - Sentry.init({ dsn, tracesSampleRate: 0.1, replaysSessionSampleRate: 0, replaysOnErrorSampleRate: 1.0, environment: process.env.NODE_ENV })
       - Low trace sample rate (0.1) to stay within free tier limits

    4. Create sentry.server.config.ts (project root):
       - Import * as Sentry from "@sentry/nextjs"
       - Guard: only init if process.env.SENTRY_DSN is set
       - Sentry.init({ dsn: process.env.SENTRY_DSN, tracesSampleRate: 0.1, environment: process.env.NODE_ENV })

    5. Create sentry.edge.config.ts (project root):
       - Import * as Sentry from "@sentry/nextjs"
       - Guard: only init if process.env.SENTRY_DSN is set
       - Sentry.init({ dsn: process.env.SENTRY_DSN, tracesSampleRate: 0.1 })

    6. Update next.config.ts:
       - Import { withSentryConfig } from "@sentry/nextjs"
       - Wrap the final export: withSentryConfig(withNextIntl(nextConfig), sentryOptions)
       - sentryOptions: { silent: true, org: "", project: "", disableSourceMapUpload: true }
         (source maps disabled by default — enable in CI with SENTRY_AUTH_TOKEN)
       - Update CSP connect-src to add "https://*.ingest.sentry.io" for Sentry event reporting
       - Avoid: Do NOT add Sentry to script-src (SDK is bundled, not loaded externally)

         ```
           // existing pg-boss init
         }
         if (process.env.NEXT_RUNTIME === "edge") {
           await import("../sentry.edge.config");
         }
         ```

    Avoid:

    - Do NOT use high sample rates — free tier has 5K error events/month
    - Do NOT upload source maps in local builds — CI only

<task type="auto">
  <name>Task 2: Add request ID propagation in middleware</name>
  <files>src/middleware.ts</files>
  <action>
    1. In the middleware function, generate a request ID at the start:
       - const requestId = request.headers.get("x-request-id") ?? crypto.randomUUID()
       - This preserves upstream request IDs (from load balancers) or generates new ones

    2. For all responses (both NextResponse.next() and NextResponse.redirect()):
       - Clone the response to add headers
       - Set x-request-id header on the response
       - For NextResponse.next(): use requestHeaders to forward the ID downstream

    3. Specifically for the NextResponse.next() calls:
       - Create request headers object: const requestHeaders = new Headers(request.headers)
       - requestHeaders.set("x-request-id", requestId)
       - Return NextResponse.next({ request: { headers: requestHeaders }, headers: { "x-request-id": requestId } })

    4. For redirect responses:
       - Set response header: response.headers.set("x-request-id", requestId)

    Avoid:
    - Do NOT import node:crypto (edge runtime) — use global crypto.randomUUID()
    - Do NOT use pino logger in middleware (edge runtime incompatible)
    - Do NOT break existing session cookie check logic

  </action>
  <verify>
    - pnpm build succeeds (middleware compiles for edge runtime)
    - curl -I http://localhost:3000/api/health shows x-request-id in response headers
    - curl -H "x-request-id: test-123" http://localhost:3000/api/health echoes the provided ID
  </verify>
  <done>AC-4 satisfied: Request IDs generated and propagated</done>
</task>
