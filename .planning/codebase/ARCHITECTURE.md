# Architecture

**Analysis Date:** 2026-02-22

## Pattern Overview

**Overall:** Server-centric layered architecture (Next.js App Router) with application-level tenant isolation, security-first design, and multi-domain modular organization.

**Key Characteristics:**

- **Server-component-first:** SSR with pre-fetched data, zero loading flash, security checks before render
- **Tenant isolation at application level:** WHERE tenantId = ? in every DAL query; no PostgreSQL RLS policies exist
- **Security-by-default:** Session validation at middleware (Layer 1) and layout (Layer 2), permission checks in server actions, role-based navigation
- **Domain-driven structure:** 18 feature domains (Observations, Compliance, Audit Execution, RAM, etc.) each with co-located actions + data-access
- **Edge-compatible routing:** Middleware runs on Edge runtime for lightweight session checks; full auth only in server contexts
- **Immutable audit trail:** Every mutation tracked via `setAuditContext()` + `AuditLog` table

## Layers

**Presentation Layer (App Router + Components):**

- Purpose: Server components (pages, layouts) that fetch data via DAL + render UI; client components for interactivity
- Location: `src/app/`, `src/components/`
- Contains: Pages (`[...]/page.tsx`), layouts with guards (`[...]/layout.tsx`), error boundaries, domain-specific UI components
- Depends on: Data-access layer, Guards, Stores (Zustand), Hooks
- Used by: HTTP clients, browsers

**Data-Access Layer (DAL):**

- Purpose: Tenant-scoped database queries with WHERE clauses; NEVER accept tenantId from URL/body — only from session
- Location: `src/data-access/` (39 files: `audit-execution.ts`, `observations.ts`, `compliance.ts`, etc.)
- Contains: Query functions that take Session object, return plain objects
- Depends on: `prismaForTenant(tenantId)`, session helpers
- Used by: Pages, server actions

**Business Logic Layer:**

- Purpose: Domain-specific stateless functions — escalation, risk rating, compliance status, housekeeping rules
- Location: `src/lib/` (engines: `escalation-engine.ts`, `housekeeping-engine.ts`, `ram-engine.ts`, `kri-engine.ts`; services: `notification-service.ts`)
- Contains: Pure functions, decision logic, no database access
- Depends on: Type definitions only
- Used by: Server actions, DAL functions, background jobs

**Server Actions (Mutations):**

- Purpose: Form submissions, database writes with auth + permission checks + audit logging
- Location: `src/actions/` (81 files across 18 domains)
- Pattern: Always `getRequiredSession()` → permission check → validate input (Zod) → db transaction → `setAuditContext()` → revalidate cache
- Depends on: DAL for queries, Guards for permission checks, Prisma for writes
- Used by: Client components (form handlers), API routes

**Background Jobs:**

- Purpose: Async workers for escalation, notifications, metric snapshots — runs outside request cycle
- Location: `src/jobs/` (7 files); registered in `src/instrumentation.ts`
- Queue: pg-boss (PostgreSQL-backed job queue)
- Depends on: Prisma, DAL, business logic engines
- Used by: Cron routes (`/api/cron/*`), manual job triggers

**API Routes (REST):**

- Purpose: Health checks, exports, report generation, cron webhooks
- Location: `src/app/api/`
- Pattern: GET for reads (health, exports), POST for cron triggers; always validate session in middleware + route handler
- Depends on: DAL, business logic, file storage (S3)
- Used by: External systems, health probes, SPA exports

**Type System:**

- Purpose: Shared TypeScript types across layers
- Location: `src/types/`, `src/generated/prisma/` (auto-generated by Prisma)
- Contains: Domain types, API request/response shapes, form schemas (Zod)
- Depends on: Prisma enums (Role, Severity, Status enums)
- Used by: All layers

**Authentication & Authorization:**

- Purpose: Session management (Better Auth), permission system (RBAC), role-based access control
- Location: `src/lib/auth.ts` (Better Auth config), `src/lib/permissions.ts` (RBAC), `src/lib/guards.ts` (route guards), `src/lib/auth-lockout-plugin.ts` (rate limit + lockout)
- Features: Email/password auth, bcrypt hashing, session cookies (`__Secure-better-auth.session_token`), rate limiting (10 login attempts per IP per 15 min), account lockout (5 failures → 30 min lock), max 2 concurrent sessions per user, 17 roles × 60+ granular permissions
- Used by: Middleware, all pages, server actions

## Data Flow

**Read Flow (SSR with Pre-fetch):**

1. Request hits middleware (Edge)
   - Check session cookie (lightweight)
   - Attach request ID for tracing
   - Redirect to /login if no cookie
2. Page server component runs
   - Call `getRequiredSession()` → full session validation
   - Call guard (e.g., `requirePermission()`) → check permission
   - Call DAL function with session object
   - DAL adds `WHERE tenantId = ?` from session
   - Prisma executes query, returns data
3. Page renders with pre-fetched data (zero loading flash)
4. Client components use TanStack Query for refetch on interaction

**Write Flow (Form Submission):**

1. Client submits form (client component)
   - Optimistic update (Zustand store)
   - Call server action with validated input (react-hook-form + Zod)
2. Server action runs
   - `getRequiredSession()` → auth check
   - Check permission (e.g., `hasPermission(roles, "observation:create")`)
   - Validate input via Zod schema
   - Get tenant-scoped Prisma client: `db = prismaForTenant(tenantId)`
   - Wrap in `$transaction()` → `setAuditContext()` → create/update records
   - Return `{ success: true, data }` or `{ success: false, error }`
3. Client receives response
   - If success: revalidate cache (ISR), show toast, navigate
   - If error: show error toast, revert optimistic update

**State Management:**

- **Server state:** Queries via TanStack Query (`@/providers/query-provider.tsx`); refetch on form mutation
- **Client state:** Zustand stores (`@/stores/`); minimal — mainly onboarding wizard state
- **Session state:** Better Auth session cookies; read-only from client (via cookie), validated server-side
- **Cache invalidation:** `revalidatePath()` in server actions triggers ISR rebuild

## Key Abstractions

**Session (AuthSession type):**

- Purpose: Authenticated user context — tenantId, roles, userId, sessionId
- Examples: `src/lib/auth.ts` (auth config), `src/data-access/session.ts` (helpers)
- Pattern: `getRequiredSession()` → returns AuthSession; cast at boundary only
- Usage: Every DAL function, server action, page guard receives session object

**Guard Functions:**

- Purpose: Route-level auth + permission checks with auto-redirect
- Examples: `requirePermission("observation:create")`, `requireAnyPermission(["dashboard:auditor", "dashboard:manager"])`
- Pattern: `src/lib/guards.ts`; return session or redirect(/login)
- Usage: Server component page entries

**DAL Functions:**

- Purpose: Tenant-scoped queries with tenant ID from session only
- Examples: `getObservations(session)`, `getComplianceItems(session)`, `getAuditEngagements(session)`
- Pattern: Accept Session, call `prismaForTenant(session.user.tenantId)`, add WHERE clauses, return plain data
- Files: `src/data-access/*.ts` (one per domain)

**Server Actions:**

- Purpose: Validated, permission-checked mutations with audit logging
- Examples: `createObservation(input)`, `updateComplianceStatus(id, status)`, `approveObservation(id)`
- Pattern: Export async function marked `"use server"`, return `{ success, data?, error? }`
- Files: `src/actions/**/*.ts` (organized by domain)

**Business Logic Engines:**

- Purpose: Domain-specific decision logic (pure, no DB access)
- Examples:
  - `computeEscalation(createdAt, dueDate, level)` → escalation level change
  - `computeRiskScore(17 parameters)` → RAM audit risk score
  - `computeComplianceStatus(...)` → observation compliance status
  - `housekeepingRules(...)` → determine required housekeeping
- Location: `src/lib/*-engine.ts`
- Pattern: Pure functions, deterministic, testable

**Form Validation (Zod):**

- Purpose: Runtime schema validation for server actions + client forms
- Examples: `CreateObservationSchema`, `UpdateComplianceSchema`
- Pattern: Zod schema in `src/actions/[domain]/schemas.ts`, use with `react-hook-form` + `@hookform/resolvers`
- Usage: Every server action

## Entry Points

**Web Application Entry:**

- Location: `src/app/page.tsx`
- Triggers: User visits https://aegis.nexlyadvisory.com
- Responsibilities: Redirect /login
- Flow: page.tsx → redirect("/login") → LoginPage (client) → form submission → auth API → session created → redirect(/dashboard)

**Dashboard (Main App):**

- Location: `src/app/(dashboard)/layout.tsx` + `src/app/(dashboard)/dashboard/page.tsx`
- Triggers: User navigates to /dashboard or any authenticated route
- Responsibilities: Layer 2 session validation, role-based sidebar nav, layout structure
- Flow: Request → middleware (Layer 1 cookie check) → layout (Layer 2 full validation) → children render with data

**Audit Execution (Complex Domain):**

- Location: `src/app/(dashboard)/audit-execution/[engagementId]/sections/[sectionCode]/page.tsx`
- Triggers: User clicks "Start Audit" on engagement card
- Responsibilities: Render examination items, collect responses, track completion
- Flow: Page server component → getAuditExaminationItems(engagementId, sectionCode) → render dynamic form → submit → updateExaminationResponse() action → revalidate

**API Health Check:**

- Location: `src/app/api/health/route.ts`
- Triggers: Uptime monitor, load balancer probes
- Responsibilities: Check DB connectivity, job queue health, memory usage
- Flow: GET /api/health → checkDatabase() + checkJobQueue() + checkMemory() → return { status, checks }

**Cron Jobs:**

- Location: `src/app/api/cron/escalation/route.ts`
- Triggers: External cron service (e.g., EasyCron) at scheduled time
- Responsibilities: Compute escalation levels, insert audit logs, enqueue notifications
- Flow: GET /api/cron/escalation → load compliance items → computeEscalation() → update DB → revalidate cache

**Background Jobs (pg-boss):**

- Location: `src/jobs/` + `src/instrumentation.ts`
- Triggers: enqueueJob() calls from server actions / cron routes
- Responsibilities: Send emails, batch notifications, compute metrics
- Pattern: Register workers in `startWorkers()`, subscribe to job names, pull from pgboss.job table

## Error Handling

**Strategy:** Fail-safe with graceful degradation. Never expose internals to client. Return structured error responses.

**Patterns:**

- **Server actions:** `{ success: false, error: string }` on validation/auth failures; try-catch logs error, returns user-friendly message
- **Pages:** Error boundary (`error.tsx`) catches server component throws, shows fallback UI
- **API routes:** `NextResponse.json({ error }, { status: 40x/50x })`
- **Middleware:** Lightweight — only redirect on missing session; full validation in layout
- **Logging:** pino logger (`src/lib/logger.ts`) logs all errors with context; Sentry for production
- **Audit trail:** Failed operations still create AuditLog entries (success: false) for forensics

**Cross-Cutting Concerns:**

**Logging:**

- Via `src/lib/logger.ts` (pino + pino-pretty in dev)
- Log request ID (attached in middleware) with every log
- Log query performance in dev mode (via Prisma log config)

**Validation:**

- Zod schemas in `src/actions/[domain]/schemas.ts`
- Server action input validation before permission check
- Database constraints (NOT NULL, UNIQUE, foreign keys) as final safety net

**Authentication:**

- Middleware cookie check (optimistic)
- Layout session validation (authoritative)
- Server action + API route session validation
- Three layers = defense in depth

## Security Model

**Tenant Isolation (Skeptic S2):**

- tenantId MUST come from authenticated session ONLY
- NEVER pass from URL params, query string, or request body
- Every DAL query adds `WHERE tenantId = session.user.tenantId`
- Enforced at application level (no PostgreSQL RLS — policies don't exist)

**Permission System (D13, D20):**

- 17 roles × 60+ granular permissions
- Multi-role support: user.roles is Role[] (union of all permissions)
- Check: `hasPermission(roles, "action:name")`
- Guard function wraps permission check with auto-redirect

**Rate Limiting (Phase 11 SC-1):**

- 10 login attempts per IP per 15 minutes
- 3 signup attempts per IP per minute
- In-memory storage (no database overhead)

**Account Lockout (Phase 11 SC-2):**

- 5 failed login attempts → 30-minute lock
- FailedLoginAttempt table tracks attempts per user + IP
- Unlock when lockout_expires passes

**Session Management (Phase 11 SC-3, SC-4):**

- Max 2 concurrent sessions per user (via multiSession plugin)
- Cookies: httpOnly, secure (production), sameSite=lax
- Idle timeout: 30 minutes
- Session table backed by database

**Audit Trail (D28):**

- Every mutation creates AuditLog entry: `{ actionType, userId, tenantId, changes, createdAt }`
- Set via `setAuditContext()` in server action transaction
- Immutable (append-only)

## v6.0 RBIA Redesign Notes

- **Dual models:** Old `ExaminationArea`/`ExaminationItem` coexist with new `ExaminationNode`/`ExaminationResponse`
- **ExaminationNode:** Hierarchical tree (max depth 5), materialized path (`path` field)
- **4-point scoring:** FULLY/LARGELY/PARTIALLY/NON_COMPLIANT → 1.0/0.75/0.5/0.0 scores, weighted roll-up
- **ActionPoint vs Observation:** ActionPoints are operational findings (~15-40/audit), Observations are formal (~3-10/audit)
- **EngagementStatus:** 8 states (PLANNED → TEAM_ASSIGNED → OPENING_MEETING → IN_PROGRESS → EXIT_MEETING → REPORT_DRAFT → COMPLETED)
- **BranchRbiaScore:** Immutable JSONB snapshot at engagement completion for historical record
- **Additive schema:** v6.0 models added alongside old models; both coexist until Phase 6 cleanup
